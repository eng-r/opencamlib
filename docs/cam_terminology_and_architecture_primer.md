# A First Journey Through CAM Terms and OpenCAMLib’s Architecture

If you are expert in another field and completely new to computer-aided manufacturing, the first useful idea is that this software is about planning motion before any machine physically moves. In OpenCAMLib, the planned motion is represented as geometric results such as cutter-location points and loops, and this intent is stated directly in the project introduction where OpenCAMLib is described as a library for creating 3D toolpaths for CNC machines and supporting drop-cutter and push-cutter algorithms. The same introduction also says the implementation is in C++ with bindings for Python, Node.js, and browser use, so one computational engine is meant to be reused in several runtime worlds rather than rewritten from scratch each time.

A toolpath, in plain words, is the route a cutting tool should follow in three-dimensional space. OpenCAMLib’s examples make this concrete by constructing an `ocl.Waterline`, attaching an STL surface and a cutter, setting sampling, running the algorithm, and retrieving loops per z-height. In that sequence you can see toolpath generation as an execution process: choose geometry, choose tool, choose fidelity, run computation, consume path output. The library itself does not claim that this output is already a complete machine program with every shop-floor decision encoded; the examples explicitly discuss additional decisions like loop ordering and start/end moves.

To understand “drop-cutter style,” imagine choosing an `(x, y)` location and lowering the cutter on the z-axis until it touches the model without gouging it. That description appears in the README and is implemented through `ocl::MillingCutter::dropCutter` together with operation classes such as `ocl::PointDropCutter`, `ocl::BatchDropCutter`, `ocl::PathDropCutter`, and `ocl::AdaptivePathDropCutter`. The term “drop-cutter logic” therefore means the family of computations that determine safe cutter z-values for one point, many points, or sampled paths.

“Push-cutter style” is different in direction but similar in spirit. Instead of dropping vertically, the cutter is pushed along a line-like primitive while checking where interference would occur. In OpenCAMLib this appears in `ocl::BatchPushCutter`, which consumes many `ocl::Fiber` objects and updates them with interval data. A `Fiber` is documented as a line along which a cutter can be pushed into contact, and waterline generation uses many x-direction and y-direction fibers, later woven into loops.

When people mention “other styles” in CAM, they usually mean alternate path generation patterns beyond these two families, and OpenCAMLib’s algorithm surface shows at least waterline and zigzag classes in addition to the drop-cutter and push-cutter machinery. In this codebase, however, these styles still live under a shared architectural shell through `ocl::Operation`, so the style may differ while the lifecycle contract remains recognizable.

Now we can define “cutter models.” A cutter model is the mathematical shape behavior of a tool, encoded so contact can be computed robustly. OpenCAMLib names several models in the README, and the base class `ocl::MillingCutter` exposes polymorphic geometry behavior through methods such as `dropCutter`, `pushCutter`, `facetDrop`, `edgeDrop`, and shape-specific width/height helpers. In practical terms, normalization of cutter behavior means every algorithm talks to a common cutter interface, while each cutter subtype supplies its own geometry math behind that interface. This is why a single algorithm can often work with multiple cutter shapes once they inherit the same core contract.

The phrase “orchestration in this context” means organizing lower-level geometric tests into end-to-end algorithm pipelines. `ocl::Operation` is the orchestration base: it stores references to the mesh and cutter, controls sampling and threads, and propagates those settings into `subOp` children. In other words, orchestration is not a separate service; it is the disciplined way algorithm classes compose and configure each other so a larger workflow behaves consistently.

You asked where mesh and cutter are attached, how sampling/thread control is set, and what happens when `run` is invoked. The direct answer is in `Operation`: `setSTL` stores a surface pointer and forwards it to sub-operations, `setCutter` stores the cutter pointer and forwards it, `setSampling` and `setThreads` do the same kind of propagation, and `run` is a pure virtual function that each concrete algorithm implements. So “contract” here means: every operation must accept the same setup vocabulary and then provide algorithm-specific execution in its own `run` implementation.

In `ocl::Waterline`, invoking `run` triggers an explicit pipeline: initialize fibers from the surface bounding box and cutter radius, run two internal `BatchPushCutter` sub-operations, collect x/y fibers, then weave them into loops through `weave.build`, `weave.face_traverse`, and `weave.getLoops`. In `ocl::AdaptivePathDropCutter`, invoking `run` triggers adaptive sampling: start/end points are evaluated, midpoint contact is computed, and recursion continues until spacing and local flatness criteria are satisfied. This is a precise example of orchestration as staged execution.

The “geometric substrate” is the foundational data model used by algorithms. In OpenCAMLib this includes primitives such as `Point`, `Triangle`, `Path`, and especially `STLSurf`, which is an unordered list of triangles plus a bounding box. Calling this the “canonical in-memory scene” means most algorithms consume the same mesh container rather than translating between incompatible internal mesh formats. That is exactly what “keeps data interchange friction low inside the core”: fewer conversions, fewer adapter layers, and fewer opportunities for numeric mismatch when moving data from one algorithm to another.

The first major design principle, stated more concretely, is interface-level normalization with behavior-level specialization. The interface is normalized by `Operation` and `MillingCutter`: algorithms are configured through a shared operation lifecycle and query cutter behavior through shared method contracts. Specialization happens where it belongs: subclasses of cutters encode shape details, and subclasses of operations encode strategy details. This balances extensibility with consistency because adding a new cutter does not force rewriting every operation orchestration, and adding a new operation does not force redefining every cutter shape.

The second major design principle is progressive specialization around sampling strategy. You can see the progression in class roles: point-level drop, batch-level drop, path-level uniform sampling, and path-level adaptive sampling. Uniform path sampling applies a fixed interval policy, while adaptive sampling recursively inserts more evaluations only where geometry requires finer detail, bounded by minimum and maximum sampling controls plus a flatness predicate. Conceptually, this gives users a speed-versus-detail continuum instead of one rigid algorithm.

“KD-tree acceleration” means using spatial indexing so each cutter test sees only nearby candidate triangles rather than all triangles in the model. `BatchDropCutter::setSTL` and `BatchPushCutter::setSTL` build kd-tree structures, and run variants query overlaps before invoking expensive contact routines. “OpenMP-enabled variants” means parallel loop implementations that distribute independent iterations across CPU threads; for example `dropCutter5` and `pushCutter3` use OpenMP pragmas and thread-count controls.

“Per-sample contact” in adaptive algorithms means every sample point along a span is turned into a contact query against the surface, not guessed from neighbors. `AdaptivePathDropCutter` delegates each sample evaluation to an internal `PointDropCutter`, then uses geometric criteria to decide whether to subdivide further. This is why adaptive behavior can sharpen detail where needed while avoiding unnecessary work on flatter regions.

The “waterline path” is a constant-z contour-like toolpath family. README language describes push-cutter as creating waterline toolpaths, and the `Waterline` class itself stores a target z-height (`zh`) and returns loop structures. The generated fibers are the scan lines in x and y directions over a z-plane, created from the model bounds expanded by cutter radius. Weave processing then converts interval intersections along those fibers into closed geometric loops suitable for downstream path usage.

An “Emscripten binding table” is the explicit registry that maps C++ classes and methods into JavaScript/WebAssembly-visible types and functions. In `emscriptenlib.cpp`, the `EMSCRIPTEN_BINDINGS(opencamlib)` block binds classes such as `Operation`, `BatchDropCutter`, `PathDropCutter`, `AdaptivePathDropCutter`, and many geometry/cutter types. This is how browser code calls the same C++ core concepts without reimplementing them in JavaScript.

When we say “different strategies” in this architecture, we mean different algorithmic paths that solve related geometric planning tasks under the same object vocabulary. “Incompatible data paths” are alternative internal representations or APIs that would force costly conversion or duplicate logic between strategies. “Confounding” in this engineering context is the difficulty of comparing two strategies fairly when they differ in too many hidden factors at once; shared data structures and contracts reduce that confounding.

Finally, manufacturing policy refers to process choices that live above pure geometry computation. In the provided examples, comments explicitly mention decisions such as ordering loops across z-heights, selecting order among multiple loops at one height, and creating plunge/retract or lead-in/lead-out moves. Machine-program semantics are the meanings attached to emitted commands and motion phases when converting geometric results into executable CNC programs. OpenCAMLib contributes the geometric core and exposes enough structure to support these higher-level decisions, while examples demonstrate where those policy layers begin.

If you carry one mental model away from this primer, let it be this: OpenCAMLib is a geometric computation kernel that standardizes how algorithms are configured and how cutter/mesh physics are queried, then offers multiple strategy implementations that trade speed, detail, and output structure without abandoning a common conceptual language.
